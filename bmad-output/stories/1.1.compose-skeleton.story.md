# 1.1: Docker Compose Skeleton

**Story ID:** 1.1
**Epic:** 1 — Infrastructure & Containerization
**Slug:** compose-skeleton
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **solo builder**,
I want **a Docker Compose skeleton with `backend` and `ollama` services**,
so that **every later pipeline story has a running, one-command local stack to build on**.

## Acceptance Criteria

1. `docker-compose.yml` defines a `backend` service (builds from `backend/`) and an `ollama` service (`ollama/ollama` image) on a shared network.
2. `docker compose up` starts both services without error on a clean checkout.
3. The `ollama` service is reachable from `backend` by service name on the compose network (e.g. `http://ollama:11434`).
4. Both services define health checks so `docker compose ps` reports readiness rather than a false "started".
5. A named volume persists Ollama's pulled models across container restarts.
6. `README.md` documents the one-command startup and that the first run pulls model images.

## Tasks / Subtasks

- [ ] Write `docker-compose.yml` with `backend` + `ollama` services (AC: #1)
  - [ ] Define a shared compose network (AC: #3)
  - [ ] Define a named volume for Ollama model storage (AC: #5)
- [ ] Add health checks to both services (AC: #4)
- [ ] Create `backend/Dockerfile` sufficient to build an (initially empty) backend image (AC: #2)
- [ ] Document startup + first-run model pull in `README.md` (AC: #6)

## Dev Notes

- Two-container topology: `backend` (FastAPI + STT + TTS, in-process) and `ollama` (LLM), on a shared compose network. [Source: tech-spec.md#architecture-overview]
- Ollama serves the LLM via its own REST API on the compose network. [Source: tech-spec.md#technology-stack]
- The whole stack must run via `docker compose up` with no calls to external/cloud AI APIs at runtime; the one-time model download is the only network dependency. [Source: tech-spec.md#fr-006-fully-local-one-command-stack-must]
- `backend/Dockerfile` should install Python dependencies by scanning a `backend/requirements/*.txt` directory (e.g. `COPY backend/requirements/ /app/requirements/` then install every file found) rather than a single `requirements.txt`, so later stories (2.1, 2.2, 2.3, 3.1) can each add their own dependency file without editing the Dockerfile again. [Inference — this pattern exists specifically to keep those stories' Owned Scope disjoint; see their story files]
- Named volume for Ollama's model storage avoids re-downloading models on every container restart. [Inference]
- Exact service/network/volume names are an implementation choice for this story. [Inference]

## Testing

- **Approach:** manual/integration verification of the compose stack; there is no application logic yet to unit test.
- **Key scenarios:** `docker compose up` from a clean checkout brings up both services; `docker compose down` tears down cleanly; a second `docker compose up` reuses the cached Ollama model volume.
- **Per-AC verification:** AC#1 → inspect `docker-compose.yml` service definitions; AC#2 → run `docker compose up`, confirm no errors; AC#3 → from inside the backend container, reach `http://ollama:11434` and confirm a response; AC#4 → `docker compose ps` shows healthy status for both services; AC#5 → restart the `ollama` container, confirm previously pulled models are still present; AC#6 → manually follow the README instructions on a clean checkout.
- **Fixtures / mocks:** none — this is infrastructure, not application logic.
- **Edge cases to cover:** first run with no cached images (slow pull must not hang or fail silently); host port already in use.

## Dev Agent Record

- **Completed:** 2026-09-02
- **Files added:** `docker-compose.yml`, `backend/Dockerfile`, `backend/requirements/.gitkeep`, `README.md`
- **Implementation notes:**
  - `backend` Dockerfile installs from `backend/requirements/*.txt` (glob-based, per 1.1's Dev Notes) so 2.1/2.2/2.3/3.1 can each add their own requirements file without touching this Dockerfile again. `backend/requirements/.gitkeep` was added so the (initially empty) directory exists for `COPY requirements/ ./requirements/` to succeed at build time.
  - `backend`'s CMD is a placeholder (`python -m http.server 8000`) with a healthcheck against `/`, since the real FastAPI app and `/health` endpoint don't exist until story 1.2. 1.2 replaces both the CMD and the healthcheck target.
  - `ollama` healthcheck uses the `ollama` CLI already present in the image (`ollama list`) rather than curl/wget, avoiding an extra dependency.
  - README documents that `docker compose up` does not itself pull an LLM model — only the empty Ollama server — and gives the `docker compose exec ollama ollama pull <model>` command as a separate step.
- **Verification (live, `docker compose up -d --build`):** all 6 ACs confirmed — both services build/start cleanly; `docker compose ps` shows both `(healthy)`; `docker compose exec backend python -c "urlopen('http://ollama:11434')"` returned HTTP 200 (AC#3); `docker compose restart ollama` came back healthy with the same named volume (AC#5, confirmed via `docker volume inspect selfhostlanguage_ollama-models`); stack torn down cleanly with `docker compose down` (volume preserved, not `-v`).
- **Environment note (not a code issue):** first attempt failed with a Docker VM disk I/O error, traced to the host Mac being at 99% disk capacity (163MB free of 228GB) plus a stale Docker Desktop containerd metadata-DB error from that failed write. Resolved by the user freeing host disk space and a full Docker Desktop restart; no changes to the compose/Dockerfile were needed once that was fixed.
- **Outcome:** success.
