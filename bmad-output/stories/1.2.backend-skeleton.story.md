# 1.2: Backend Application Skeleton

**Story ID:** 1.2
**Epic:** 1 — Infrastructure & Containerization
**Slug:** backend-skeleton
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **solo builder**,
I want **a minimal FastAPI application skeleton with clear module seams**,
so that **subsequent pipeline, scenario, and API stories have a stable place to add code**.

## Acceptance Criteria

1. `backend/app/main.py` exposes a FastAPI app that starts under the `backend` container from 1.1.
2. A `/health` endpoint returns 200, confirming the app is running.
3. `backend/app/api/router.py` exists as an empty router aggregator, included once by `main.py`, so later stories can add routes without editing `main.py` again.
4. Empty package stubs exist for `app/api/`, `app/pipeline/`, `app/scenarios/`, `app/state/`.
5. `main.py` mounts `frontend/` as static files, so later frontend stories (Epic 4) need no backend changes to be served.
6. `docker compose up` (from 1.1) now serves the FastAPI app and `/health` responds successfully.

## Tasks / Subtasks

- [ ] Scaffold the FastAPI app factory and entrypoint (AC: #1)
- [ ] Add `/health` endpoint (AC: #2)
- [ ] Create `app/api/router.py` as an empty `APIRouter`, included by `main.py` (AC: #3)
- [ ] Create empty `api/`, `pipeline/`, `scenarios/`, `state/` package stubs (AC: #4)
- [ ] Mount `frontend/` as static files in `main.py` (AC: #5)
- [ ] Wire the uvicorn entrypoint into `backend/Dockerfile` from 1.1 (AC: #6)

## Dev Notes

- Backend is FastAPI + uvicorn. [Source: tech-spec.md#technology-stack]
- Backend Orchestrator responsibilities: serve the static frontend, serve the scenario list, and coordinate a conversation turn. [Source: tech-spec.md#backend-orchestrator-faststapi]
- `app/api/router.py` is introduced specifically so that 3.3 (scenario/session routes) and 2.4 (turn route) can each extend one aggregator file in sequence (3.3 first, then 2.4) instead of both editing `main.py`; `main.py` itself is only ever touched by this story. [Inference — this is the mechanism that keeps later stories' Owned Scope disjoint from `main.py`]
- No central `config.py` is introduced here on purpose: each later module (STT, LLM, TTS, scenarios) reads its own environment variables directly within its own owned file, so config additions don't force multiple stories to edit a shared config module. [Inference]
- Package layout (`app/api`, `app/pipeline`, `app/scenarios`, `app/state`) mirrors the components tech-spec.md describes (Backend Orchestrator, Scenario Engine, STT/LLM/TTS pipeline). [Source: tech-spec.md#key-components]

## Testing

- **Approach:** unit test for `/health`; a smoke test that the app imports and starts cleanly.
- **Key scenarios:** app starts without error; `/health` returns 200; the empty router mounts without error; static files are served from `frontend/`.
- **Per-AC verification:** AC#1 → app import + TestClient smoke test; AC#2 → `TestClient` GET `/health` == 200; AC#3 → assert `router.py` is importable and included in the app's routes; AC#4 → structural check that all four packages exist and import cleanly; AC#5 → TestClient GET of a known static path (e.g. a placeholder `frontend/index.html`) returns 200; AC#6 → manual `docker compose up`, curl `/health` from the host.
- **Fixtures / mocks:** FastAPI `TestClient`.
- **Edge cases to cover:** `frontend/` directory not yet populated (mount should not error on an empty/near-empty directory).
