# 2.2: Local LLM Integration via Ollama

**Story ID:** 2.2
**Epic:** 2 — Voice Pipeline
**Slug:** llm-integration
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As the **backend orchestrator**,
I want **to call a local LLM via Ollama to generate a reply to a given prompt**,
so that **the pipeline can produce the AI's side of the conversation**.

## Acceptance Criteria

1. A `generate_reply(prompt: str) -> str` function in `app/pipeline/llm.py` calls the Ollama container's REST API and returns the model's text reply.
2. The Ollama base URL and model name are read from environment variables (with sensible defaults), not hardcoded inline.
3. Given a simple test prompt, `generate_reply()` returns a non-empty text reply from the configured model.
4. An unreachable or erroring Ollama instance raises a clear, catchable error within a bounded timeout, rather than hanging indefinitely or crashing the process.
5. No call is made to any LLM API outside the local `ollama` compose service.

## Tasks / Subtasks

- [ ] Implement the Ollama HTTP client call in `app/pipeline/llm.py` (AC: #1, #5)
- [ ] Read Ollama base URL / model name from env vars with defaults (AC: #2)
- [ ] Add a request timeout and error handling for unreachable/erroring Ollama (AC: #4)
- [ ] Add a test against a running (or mocked) Ollama instance (AC: #3)

## Dev Notes

- Ollama serves the local conversational LLM via REST API on the compose network, reachable at `http://ollama:11434` from the backend container. [Source: tech-spec.md#architecture-overview]
- LLM runtime choice: Ollama — flagged in tech-spec.md as an assumption made without explicit user confirmation; worth revisiting if the user has a different preference. [Source: tech-spec.md#assumptions]
- Intended default is a small quantized instruct model (~7-8B class), consistent with the CPU-only baseline. [Source: tech-spec.md#technology-stack]
- Local-only inference is a hard project constraint — Ollama is the only LLM endpoint this story may call. [Source: tech-spec.md#constraints]
- This story generates a reply from a raw prompt only; composing the scenario-aware prompt (persona/goal/history) is 2.4's job, using the schema from 3.1. [Inference]

## Testing

- **Approach:** integration test against a real Ollama instance where available, else a mocked HTTP client for unit coverage.
- **Key scenarios:** a simple prompt returns non-empty text; an unreachable Ollama raises a clear error within a bounded timeout; a malformed Ollama response is handled without crashing.
- **Per-AC verification:** AC#1 → call `generate_reply()` with a fixture prompt; AC#2 → assert configured values (not literals) are used in the request; AC#3 → integration test with a live or mocked Ollama; AC#4 → simulate a connection error/timeout, assert the raised exception; AC#5 → confirm the only outbound HTTP call targets the configured Ollama base URL.
- **Fixtures / mocks:** mocked HTTP responses for unit tests; optionally a real Ollama container for one integration test.
- **Edge cases to cover:** Ollama still loading/pulling a model on first run; a very long prompt; an empty prompt.
