# 2.3: Local Text-to-Speech Integration

**Story ID:** 2.3
**Epic:** 2 — Voice Pipeline
**Slug:** tts-integration
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As the **backend orchestrator**,
I want **to convert the AI's text reply into spoken audio using a local TTS model**,
so that **the user hears the reply instead of only reading it**.

## Acceptance Criteria

1. A `synthesize(text: str) -> bytes` function in `app/pipeline/tts.py` generates audio locally from input text via Piper TTS.
2. TTS runs in-process inside the `backend` container — no separate TTS service/container.
3. Given a short text string, `synthesize()` returns non-empty audio bytes in a browser-playable format (e.g. WAV).
4. Empty or invalid text input raises a clear, catchable exception rather than crashing the process.
5. No network call is made to any external TTS service during synthesis.

## Tasks / Subtasks

- [ ] Add Piper dependency in `backend/requirements/tts.txt` and load a voice model for the target language (AC: #1, #2)
- [ ] Implement `synthesize()` wrapping Piper (AC: #1)
- [ ] Handle empty/invalid text input with a clear exception type (AC: #4)
- [ ] Add a test asserting non-empty, valid-WAV audio output (AC: #3)
- [ ] Confirm no outbound network call occurs during synthesis (AC: #5)

## Testing

- **Approach:** a mocked/stubbed Piper call for fast unit coverage, plus one integration test producing real audio from a fixture string.
- **Key scenarios:** known text synthesizes to non-empty, playable audio bytes; empty text raises a clear error; the voice model loads once and is reused.
- **Per-AC verification:** AC#1 → call `synthesize()` with a fixture string; AC#2 → structural/code review confirms no separate TTS container in `docker-compose.yml`; AC#3 → integration test asserts non-empty bytes with a valid WAV header; AC#4 → test with an empty string expects a raised exception; AC#5 → assert/mock that no HTTP client is invoked during synthesis.
- **Fixtures / mocks:** a short reference text string; a mocked Piper voice for fast unit tests.
- **Edge cases to cover:** very long text; text with unsupported characters/punctuation.

## Dev Agent Record

- **Completed:** 2026-09-02
- **Files added:** `backend/app/pipeline/tts.py`, `backend/requirements/tts.txt`, `backend/tests/test_tts.py`
- **Implementation notes:**
  - Uses the `piper-tts` PyPI package's `PiperVoice.load()` / `.synthesize_wav(text, wav_file)` API against a stdlib `wave.Wave_write` writer over an `io.BytesIO()` buffer, so `synthesize()` returns real, valid WAV bytes with no temp files.
  - `PiperVoice.load()` requires the ONNX model + JSON config to already exist on disk — it does not auto-download. `_get_voice()` (the `lru_cache`-wrapped singleton, same pattern as 2.1/2.2) calls `piper.download_voices.download_voice()` on first use if the voice files aren't present in `TTS_VOICE_DIR` (default `/app/voices`), which is idempotent and skips re-downloading. Default voice is `en_US-lessac-medium`, matching the project's single-`en`-language scenarios; both `TTS_VOICE` and `TTS_VOICE_DIR` are overridable env vars, read inline per 1.2's no-central-config convention.
  - Same AC#5 interpretation as 2.1/2.2: "no network call during synthesis" covers the inference call itself, not the one-time voice-model download (analogous to Ollama's `pull` and Whisper's HF download).
- **Verification:** 5 mocked unit tests pass (empty/whitespace text raises, valid WAV bytes returned, backend-failure raises, no network call during a stubbed synthesis). Real integration test downloaded the actual Piper voice and produced genuine playable audio (`RIFF`/`WAVE` header, >1000 bytes) in ~3.7s. Full 31-test suite (1.1 through 3.3) passes together; live `docker compose up` confirms only `backend`+`ollama` run (AC#2) and `/health` stays 200.
