# 3.1: Scenario Schema and Loader

**Story ID:** 3.1
**Epic:** 3 — Scenarios
**Slug:** scenario-schema-loader
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As the **backend**,
I want **a defined scenario YAML schema and a loader that validates scenario files at startup**,
so that **scenario content can be authored as config rather than code**.

## Acceptance Criteria

1. A documented YAML schema for a scenario exists with fields: `id`, `title`, `target_language`, `persona_prompt`, `goal`, `difficulty`.
2. `app/scenarios/loader.py` loads all `*.yaml` files from a configurable scenarios directory at startup and validates them against the schema.
3. A malformed scenario file (missing required field, wrong type) fails startup with a clear error identifying the file and the problem.
4. Loaded scenarios are exposed via `get_scenario(id)` and `list_scenarios()` accessors that other modules can call.
5. An empty scenarios directory returns an empty list from the loader rather than erroring.

## Tasks / Subtasks

- [ ] Define the scenario schema (e.g. a pydantic model) (AC: #1)
- [ ] Implement directory scan + YAML parse + validation (AC: #2, #3)
- [ ] Implement `get_scenario(id)` / `list_scenarios()` accessors (AC: #4)
- [ ] Handle an empty scenarios directory gracefully (AC: #5)
- [ ] Unit tests for valid, invalid, and empty scenario sets (AC: #1-#5)

## Dev Notes

- Scenario YAML schema fields: `id`, `title`, `target_language`, `persona_prompt`, `goal`, `difficulty`. [Source: tech-spec.md#scenario-engine]
- Scenario Engine responsibility: load and validate scenario YAML files at startup. [Source: tech-spec.md#scenario-engine]
- Scenarios must be config-driven so more can be added without pipeline code changes (FR-008). [Source: tech-spec.md#fr-008-multiple-selectable-scenarios-should]
- No database — scenario definitions are static files on disk. [Source: tech-spec.md#data-model]
- Using pydantic (vs. a plain dataclass) is a reasonable choice for the schema, since it gives clearer validation errors for AC#3. [Inference]

## Testing

- **Approach:** unit tests only — no external dependencies.
- **Key scenarios:** a well-formed scenario file loads correctly; a file missing a required field fails with a clear, file-identified error; an empty directory yields an empty list.
- **Per-AC verification:** AC#1 → schema definition test (required fields enforced); AC#2 → loader test against a fixture directory of valid YAML files; AC#3 → loader test against a fixture with a deliberately malformed file, asserting the error names the file; AC#4 → call `get_scenario()`/`list_scenarios()` after loading and assert expected contents; AC#5 → loader test against an empty fixture directory.
- **Fixtures / mocks:** a small test-only fixture directory of valid/invalid scenario YAML files, separate from 3.2's real content.
- **Edge cases to cover:** duplicate scenario `id`s across files; unknown extra fields in a YAML file.

- **Implementation notes:**
  - `Scenario` (pydantic `BaseModel`) enforces all 6 required fields non-empty; unknown extra YAML keys are silently ignored (pydantic's default behavior) rather than rejected — AC#3 only requires failing on *missing*/*wrong-type* fields, not extra ones, and a test (`test_unknown_extra_field_is_ignored`) locks in that tolerance.
  - **AC#2 "at startup" without touching `main.py`:** `main.py` is owned by story 1.2 (already `done`) and this story's Owned Scope doesn't include it, so `loader.py` calls `load_scenarios()` unconditionally at *module import time* (last line of the file). Whenever something later imports `app.scenarios.loader` (e.g. 3.3 wiring scenario routes into `router.py`, which `main.py` already imports), loading happens automatically as part of that import chain — no explicit FastAPI startup hook needed. Verified this doesn't break the current app: `docker compose up` still starts and stays healthy even though nothing imports `app.scenarios` yet today.
  - Default scenario directory resolves to `/app/scenarios` inside the container (i.e. `backend/scenarios/` on the host, matching 3.2's declared paths), overridable via `SCENARIOS_DIR` env var, read inline per 1.2's no-central-config convention. Missing/empty directory returns `[]` rather than raising (AC#5) — confirmed safe since it's exactly what happens on every current `docker compose up` (no scenario content exists until 3.2).
  - Duplicate scenario `id`s across files: last file wins (sorted glob order), not an error — documented behavior, not specified by any AC, locked in by `test_duplicate_scenario_ids_last_file_wins`.
