# 3.3: Scenario List and Session-Start API

**Story ID:** 3.3
**Epic:** 3 — Scenarios
**Slug:** scenario-selection-api
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **user**,
I want **to see the list of available scenarios and start a session for one**,
so that **I can choose what to practice before I begin talking**.

## Acceptance Criteria

1. `GET /api/scenarios` returns the list of loaded scenarios (`id`, `title`, `target_language`, `difficulty`).
2. `POST /api/session/start` accepts a scenario `id` and creates a new session, returning a session `id`.
3. Starting a session with an unknown scenario `id` returns a clear 4xx error, not a server crash.
4. A newly started session's state has an empty turn history, ready for 2.4's turn endpoint to append to.
5. Concurrent sessions for different scenario choices do not interfere with each other's state.

## Tasks / Subtasks

- [ ] Implement `GET /api/scenarios`, registered on `app/api/router.py` from 1.2 (AC: #1)
- [ ] Implement a `Session` object and `create_session()` / `get_session()` in `app/state/session_store.py`, including a `.history` list attribute for 2.4 to append to later (AC: #2, #4)
- [ ] Implement `POST /api/session/start`, registered on `app/api/router.py` (AC: #2)
- [ ] Validate the scenario id exists (via 3.1's `get_scenario()`) before creating a session; return 4xx if not (AC: #3)
- [ ] Ensure session state is keyed/isolated per session id (AC: #5)
- [ ] Integration tests for both routes (AC: #1-#5)

## Dev Notes

- API contract: `GET /api/scenarios` — list available scenarios; `POST /api/session/start` — start a session for a given scenario id. [Source: tech-spec.md#backend-orchestrator-faststapi]
- Session state is in-memory, per-session, discarded on restart; no database. [Source: tech-spec.md#data-model]
- FR-001: the user can select a scenario and start a voice conversation session for it. [Source: tech-spec.md#fr-001-start-a-scenario-session-must]
- Uses `list_scenarios()` / `get_scenario()` from 3.1 rather than reading scenario files directly. [Inference]
- `session_store.py`'s `Session` object should expose a mutable `.history` list attribute now, even though this story never appends to it — 2.4 will import `get_session()` and mutate `.history` directly from its own file, so `session_store.py` needs no further edits once 2.4 lands. This keeps the two stories' Owned Scope disjoint. [Inference]
- Session id generation strategy (e.g. UUID4) is an implementation choice. [Inference]

## Testing

- **Approach:** integration tests against the FastAPI `TestClient`.
- **Key scenarios:** listing scenarios returns the real starter set (from 3.2); starting a session with a valid id succeeds and returns an id with empty history; starting a session with an invalid id returns a 4xx; two sessions started concurrently have independent state.
- **Per-AC verification:** AC#1 → GET request, assert scenario list shape/content; AC#2 → POST request, assert a session id is returned; AC#3 → POST with a bogus id, assert a 4xx and a clear error body; AC#4 → inspect the new session's state immediately after creation; AC#5 → create two sessions, mutate one's state, assert the other is unaffected.
- **Fixtures / mocks:** relies on 3.1's loader plus 3.2's real scenario files (or a small test fixture set).
- **Edge cases to cover:** starting a session before any scenarios have loaded; rapid repeated session-start calls.
