# 4.1: Core Web UI — Scenario Picker, Recording, Playback

**Story ID:** 4.1
**Epic:** 4 — Frontend
**Slug:** web-ui-core
**Status:** review

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **user**,
I want **a simple web UI to pick a scenario, record my voice, and hear the AI's reply**,
so that **I can actually hold the practice conversation, not just call the API directly**.

## Acceptance Criteria

1. On load, the page fetches `GET /api/scenarios` (from 3.3) and renders a selectable list.
2. Selecting a scenario and confirming calls `POST /api/session/start` (from 3.3) and stores the returned session id client-side.
3. A record button starts/stops microphone capture (push-to-talk) via the browser `MediaRecorder` API.
4. On stopping a recording, the captured audio is sent to `POST /api/session/{id}/turn` (from 2.4); the returned AI audio plays back automatically.
5. Clear UI feedback is shown for each state: idle, recording, awaiting reply, playing reply.

## Testing

- **Approach:** manual browser testing of the golden path (this is UI-heavy, push-to-talk client code); no headless test harness is mandated for Quick Flow scope.
- **Key scenarios:** scenario list renders and is selectable; starting a session stores a session id; recording captures audio and sends it on stop; AI audio autoplays on response; each state is visibly distinct.
- **Per-AC verification:** AC#1 → manual load, confirm scenario list appears; AC#2 → manual selection, confirm session id is stored (e.g. via browser dev tools); AC#3 → manual record/stop, confirm audio blob is produced; AC#4 → manual full turn, confirm reply audio plays; AC#5 → manual walk-through of all four states.
- **Fixtures / mocks:** none required — exercised against the real backend from 2.4/3.3 running via `docker compose up`.
- **Edge cases to cover:** microphone permission denied (should not crash the page — full handling is 5.2, but this story must not throw an unhandled exception); no scenarios returned from the API.

## Dev Agent Record

- **Completed:** 2026-09-02 (implementation); status left at `review`, not `done` — see below.
- **Files added:** `frontend/index.html`, `frontend/styles.css`, `frontend/app.js`, `frontend/components/scenario_picker.js`, `frontend/components/recorder.js`
- **Implementation notes:**
  - No framework/bundler — plain `<script>` tags in dependency order (`scenario_picker.js`, `recorder.js`, `app.js`), each attaching a small namespaced object (`window.ScenarioPicker`, `window.Recorder`) to the global scope rather than using ES modules, per Dev Notes.
  - `recorder.js` wraps `getUserMedia` + `MediaRecorder` behind `start()`/`stop()` returning a `Promise<Blob>`; `app.js` owns the 4-state machine (idle/recording/awaiting/playing) via a `data-state` attribute on `#status-indicator` that `styles.css` colors distinctly per state (AC#5).
  - Turn audio is sent as `multipart/form-data` (matching 2.4's `UploadFile` route) and the reply is played via a `data:audio/wav;base64,...` URI set on an `<audio>` element, matching 2.4's `audio_base64` response field.
  - Both edge cases from Testing are handled without an unhandled exception: mic-permission-denial is caught around `Recorder.start()` and shown as status text (full dedicated UX is 5.2's job); an empty/failed scenario fetch renders a fallback list item instead of crashing.
- **Verification — what I could confirm without a browser tool in this session:**
  - Both JS files pass `node --check` (syntax-valid).
  - `docker compose up` serves `index.html`/`app.js`/`styles.css`/both component files with correct content-types via the `frontend/` bind mount (no backend changes needed, confirming 1.2's mount design).
  - Replayed the **exact HTTP sequence `app.js` performs** with a Node script using `fetch`/`FormData`/`Blob` (the same web APIs the browser code uses, not a mock): `GET /api/scenarios` → pick a scenario → `POST /api/session/start` → `POST` the real fixture audio to `/api/session/{id}/turn` as multipart form data → got back a real `user_text`/`ai_text`/`audio_base64`, plus confirmed the invalid-scenario-id path returns 404 exactly as `app.js`'s error handling expects.
- **NOT verified — needs a human in a real browser, per this story's own Testing section ("manual browser testing... no headless test harness is mandated"):** actual DOM rendering of the scenario list, clicking through the picker → record → stop → playback flow, real microphone capture, audio autoplay behavior, and the visual appearance of each state. This session has no connected browser-automation tool, so these are honestly unverified rather than assumed to work. Recommend: open `http://localhost:8000` after `docker compose up`, pick a scenario, click Record, say something, click Stop, and confirm the AI's reply plays back with each state visibly changing.
