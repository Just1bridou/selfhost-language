# 5.1: Session End and Restart Flow

**Story ID:** 5.1
**Epic:** 5 — Polish
**Slug:** session-end-restart
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **user**,
I want **to end my current session and start a new one with a different scenario without restarting the containers**,
so that **I can practice multiple scenarios in one sitting**.

## Acceptance Criteria

1. An "end session" control is visible whenever a session is active.
2. Ending a session clears client-side session state (session id, transcript) and returns the UI to the scenario picker.
3. Picking a new scenario after ending a session calls `POST /api/session/start` (from 3.3) again, exactly as the first session start did.
4. The new session starts with empty transcript/history, with no leftover state from the previous session.
5. No container restart is required to start the new session.

## Tasks / Subtasks

- [ ] Add an "end session" control to the active-session UI (AC: #1)
- [ ] Implement client-side state reset (session id, transcript) on end (AC: #2, #4)
- [ ] Return the UI to the scenario picker view after ending a session (AC: #2)
- [ ] Reuse the existing session-start call path for the new scenario (AC: #3, #5)

## Dev Notes

- FR-009: the user can end a session and start a new one with a different scenario without restarting the containers. [Source: tech-spec.md#fr-009-restart-with-a-different-scenario-could]
- No new backend endpoint is needed: "ending" a session on the client is purely a UI-state reset, since a new `POST /api/session/start` call already creates an isolated, independent session (per 3.3's AC#5) — the backend already supports this without changes. [Inference]
- Session history is in-memory per session; old sessions are simply not referenced again by the client, consistent with the project's no-database approach. [Source: tech-spec.md#data-model]

## Testing

- **Approach:** manual browser testing on top of 4.1/4.2's golden path.
- **Key scenarios:** ending a session returns to the picker; starting a new scenario after ending produces a fresh, empty transcript; no page reload or container restart is needed.
- **Per-AC verification:** AC#1 → manual check the control appears once a session starts; AC#2 → manual end, confirm picker view and cleared state; AC#3 → manual new-scenario selection, confirm a new session-start call is made; AC#4 → manual check the new transcript is empty; AC#5 → confirm no `docker compose restart` is needed between sessions.
- **Fixtures / mocks:** none required — exercised against the real backend from 3.3.
- **Edge cases to cover:** ending a session mid-recording or mid-reply-playback (should not leave the UI in a stuck state).

## Dev Agent Record

- **Completed:** 2026-09-02 (implementation); status left at `review`, not `done` — same reason as 4.1/4.2.
- **Files edited:** `frontend/app.js` (new `endSessionBtn`, `endSession()`), `frontend/components/scenario_picker.js` (new `reset()`) — both within declared shared/contended scope. No `index.html`/`styles.css` edits needed this time.
- **Implementation notes:**
  - The "End session" button is created and inserted by `app.js` directly into `#conversation` rather than declared in `index.html` — since that section is already only ever visible while a session is active, this satisfies AC#1 with no separate show/hide logic, and avoids yet another cross-story `index.html` edit. The existing generic `button { ... }` CSS rule in `styles.css` already styles it with no changes needed there either.
  - `endSession()`: best-effort stops an in-flight recording (releases the mic) and clears/pauses `replyAudio` if a reply was mid-playback, then clears `sessionId`, the transcript, and the scenario picker's selection, and swaps the two `<section>`s back to the picker view (AC#2, #4). Deliberately does not attempt to cancel an in-flight `/turn` fetch (edge case scope: "should not leave the UI in a stuck state," not "must cancel the network request") — the UI itself is fully reset and usable immediately either way.
  - AC#3/#5 need no new code: `ScenarioPicker.init()` wires `startBtn`'s click listener once at page load, and that listener still calls the same `startSession()` after the picker is re-shown, so a new `POST /api/session/start` happens exactly as the first time, with no container involvement.
  - `scenario_picker.js`'s new `reset()` clears the closure's `selectedScenarioId`, re-disables `startBtn`, and unchecks any selected radio — so the picker looks and behaves like a fresh page load, not like it remembers the ended session's choice.
- **Verification:** both edited files pass `node --check`; confirmed via `curl` that the live (bind-mounted, no rebuild needed) `app.js`/`scenario_picker.js` being served include the new code.
- **NOT verified — needs a human in a real browser, same limitation as 4.1/4.2:** clicking End session mid-idle, mid-recording, and mid-playback; confirming the picker view reappears with no scenario pre-selected; confirming a fresh session truly starts with an empty transcript; confirming no container restart was needed (trivially true here since nothing touches Docker, but worth eyeballing).
- **Outcome:** success. User confirmed working in a real browser on 2026-09-02; flipped to `done`.
