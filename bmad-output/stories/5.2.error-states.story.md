# 5.2: User-Facing Error States

**Story ID:** 5.2
**Epic:** 5 — Polish
**Slug:** error-states
**Status:** done

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **user**,
I want **clear on-screen messages when something goes wrong**,
so that **the app degrades gracefully instead of silently failing or freezing**.

## Acceptance Criteria

1. If the browser denies microphone permission, the UI shows a clear message explaining recording is unavailable, instead of failing silently.
2. If a turn request fails because a pipeline stage errored (per 2.4's AC#5 error responses), the UI shows a clear, non-technical error message and returns to a usable state (not stuck in "awaiting reply").
3. If `GET /api/scenarios` or `POST /api/session/start` fails (e.g. backend not yet ready), the UI shows a clear retry-able message rather than a blank screen.
4. Error messages are dismissible and do not block the user from retrying the action that failed.
5. No unhandled JavaScript exception reaches the browser console as the sole feedback for any of the above cases.

## Tasks / Subtasks

- [ ] Handle mic-permission-denied in the recorder flow with a visible message (AC: #1, #5)
- [ ] Handle turn-endpoint failure responses (from 2.4) with a visible message and state reset (AC: #2, #4, #5)
- [ ] Handle scenario-list/session-start failures with a visible, retry-able message (AC: #3, #4, #5)
- [ ] Add a shared dismissible error-message UI element reused across the above (AC: #4)

## Dev Notes

- Backend surfaces pipeline failures (mic permission is a browser-only concern; STT/LLM/TTS/session errors) as clear, user-facing status rather than silent failures or raw stack traces — this story is the frontend half of that contract. [Source: tech-spec.md#error-handling-strategy]
- 2.4's AC#5 guarantees a clear error response (not a partial result) for any pipeline-stage failure; this story only needs to surface that response, not invent new backend error handling. [Source: tech-spec.md#backend-orchestrator-faststapi] [Inference: cross-referencing 2.4's story contract]
- 3.3's AC#3 guarantees a clear 4xx for an invalid scenario id; this story surfaces failures from that and from basic connectivity issues (backend not ready yet). [Inference]
- No formal accessibility target beyond the transcript captioning already covered by 4.2; this story is about failure visibility, not a full accessibility pass. [Source: tech-spec.md#accessibility--compliance]

## Testing

- **Approach:** manual browser testing, deliberately triggering each failure mode.
- **Key scenarios:** denying mic permission shows a message and doesn't crash the page; stopping the `ollama` container mid-session and submitting a turn shows a clear error and returns the UI to a usable state; loading the page before the backend is ready shows a retry-able message.
- **Per-AC verification:** AC#1 → manually deny mic permission in the browser, confirm the message; AC#2 → manually induce a pipeline failure (e.g. stop `ollama`), confirm the message and recovered UI state; AC#3 → manually load before backend readiness, confirm the message; AC#4 → confirm each message can be dismissed and the underlying action retried; AC#5 → check the browser console shows no unhandled exceptions during any of the above.
- **Fixtures / mocks:** none required — exercised against the real backend, deliberately degraded (e.g. stopping the `ollama` container) to trigger failures.
- **Edge cases to cover:** two failures in quick succession (e.g. mic denied, then a turn failure) should not stack conflicting messages confusingly.

## Dev Agent Record

- **Completed:** 2026-09-02 (implementation); status left at `review`, not `done` — same reason as the rest of Epic 4/5's frontend stories.
- **Files edited:** `frontend/app.js`, `frontend/components/recorder.js`, `frontend/styles.css` (all in declared scope). Also `frontend/components/scenario_picker.js` — deviation, see below.
- **Implementation notes:**
  - Built a single shared, dismissible `#error-banner` (AC#4) created and inserted by `app.js` right after the `<h1>`, so it's visible above either section regardless of which is showing. Every failure path now routes through `showError()`/`hideError()` instead of overloading the recording-state indicator's text, which was the pre-existing (informal) error surfacing this story replaced.
  - **AC#1:** `recorder.js`'s `start()` now catches `getUserMedia` rejections itself and rethrows a friendly, cause-specific message (`NotAllowedError`/`SecurityError` → permission-denied wording; `NotFoundError` → no-microphone wording; anything else → a generic fallback), so the friendliness lives with the code that actually knows the error taxonomy.
  - **AC#2:** added `friendlyTurnError()` in `app.js`, mapping the backend's known per-stage `detail` prefixes (`"speech-to-text failed"`, `"language model failed"`, `"text-to-speech failed"`, `"no active session"`/`"scenario "`) to non-technical phrasing, since the raw backend `detail` string is accurate but leaks internals (e.g. `"language model failed: failed to reach Ollama at http://ollama:11434/api/generate: [Errno -2] Name or service not known"`) — confirmed this exact string live by stopping the `ollama` container mid-turn (see Verification). Falls back to a generic message for any unrecognized detail rather than ever showing the raw string.
  - **AC#3:** `startSession()` now catches both network-level fetch failures and non-2xx responses, calling `showError()` and returning (never throwing) — no retry button needed here since the user never leaves the picker on failure, so clicking "Start session" again *is* the retry. The scenario-*list*-load failure is different (no button exists yet if the list itself failed to render), so this required a **scope deviation**: added a `Retry` button to `scenario_picker.js`'s `renderLoadError()` that re-invokes the same load function — `scenario_picker.js` was not in this story's declared Owned Scope, but AC#3 explicitly covers `GET /api/scenarios` failures and there was no other file where that retry logic could live.
  - **AC#5:** every `await` in the changed code is now inside a `try/catch` or calls a function that already contract-guarantees it never throws (`startSession`, `loadScenarios`); `window.Recorder.stop()` in `endSession()` already had `.catch(() => {})` from 5.1; added a `try/catch` around `replyAudio.play()` too (a rejected autoplay was previously unhandled) so a blocked/failed playback surfaces via the banner instead of an unhandled rejection.
  - **Edge case (no message-stacking):** since there's exactly one `#error-banner` whose text is replaced (not appended to) on each `showError()` call, two failures in quick succession simply show the latest one — never multiple stacked messages.
- **Verification:**
  - All 3 edited/new JS files pass `node --check`.
  - Confirmed via `curl` that the live (bind-mounted) files serve the new code (`error-banner` in `app.js`, `Retry` in `scenario_picker.js`, `NotAllowedError` in `recorder.js`).
  - **Live-verified AC#2's exact failure shape:** stopped the `ollama` container, replayed the turn-submission HTTP call with real fixture audio via Node — got back `HTTP 502 {"detail":"language model failed: failed to reach Ollama at http://ollama:11434/api/generate: [Errno -2] Name or service not known"}`, confirmed `friendlyTurnError()` matches this exact string via its `"language model failed"` prefix check, then restarted `ollama` and confirmed it came back healthy.
- **NOT verified — needs a human in a real browser, same limitation as the rest of Epic 4/5:** actually denying mic permission and seeing the banner; dismissing a banner and confirming the underlying action can be retried; the "two failures in quick succession" edge case visually.
- **Bug found from user testing, fixed:** the "Dismiss" button never actually hid the banner. Root cause: `#error-banner { display: flex; }` (ID selector, specificity 1-0-0) has higher specificity than the browser's built-in `[hidden] { display: none }` rule (0-1-0), so setting `errorBanner.hidden = true` in JS correctly set the HTML attribute but the CSS cascade still rendered it as `flex`. Fixed by adding `#error-banner[hidden] { display: none; }` (specificity 1-1-0, wins regardless of source order). Checked every other element toggled via `.hidden` in the codebase (`#scenario-picker`, `#conversation`) — both are styled only via the generic `section {}` rule, which never sets `display`, so neither had this trap.
- **Outcome:** success. User confirmed working in a real browser on 2026-09-02 (after finding and fixing the Dismiss-button CSS specificity bug above); flipped to `done`. This was the last story in the backlog.
