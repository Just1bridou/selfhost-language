# 7.1: See and Change the AI Models

**Story ID:** 7.1
**Epic:** 7 — Model Configuration & Difficulty
**Slug:** model-configuration
**Status:** review

> Added after the original backlog completed. Sized to one dev-day (~2-8h).
> No story points.

## Story

As a **user**,
I want **to see which AI models are running and change them from the app**,
so that **I can upgrade to a better model without editing config files or restarting containers**.

## Acceptance Criteria

1. A settings panel shows all three engines (speech-to-text, language model, voice) with the model currently in use for each.
2. The speech-to-text model size and the per-language voice can each be changed and are used by the next turn.
3. The language model can be changed to any model Ollama has installed; the panel warns when the configured model is not installed.
4. A curated catalogue of additional models — including small Gemma models — can be browsed and downloaded from the panel, with live progress, without using a terminal.
5. Settings persist across a container restart rather than reverting to defaults.
6. Invalid values (unknown STT size, a voice that belongs to another language, an unknown language) are rejected with a clear message and never applied.

## Tasks / Subtasks

- [ ] Add a persisted settings store, seeded from the existing env-var defaults (AC: #5, #6)
- [ ] Read the STT size, LLM model and TTS voice from settings in the pipeline, caching per value (AC: #2, #3)
- [ ] Add `GET`/`PUT /api/models` reporting and updating all three engines (AC: #1, #2, #6)
- [ ] Add a curated model catalogue and a background pull endpoint with progress polling (AC: #4)
- [ ] Build the settings panel UI with per-engine controls and the download list (AC: #1-#4)

## Dev Notes

- The three models were previously fixed by env vars read at call time — `STT_MODEL_SIZE`, `OLLAMA_MODEL` and the per-language voice from the registry. Those become *defaults*; overrides live in the settings store. [Inference]
- Piper voices are per language, so "change the voice" is a per-language choice, not one global value — the registry gains a curated `voices` list per language. Curated rather than fetched from the Piper index at runtime, so the app stays usable offline, consistent with the project's local-only constraint. [Source: tech-spec.md#constraints]
- Pulling a model is a multi-GB download; it must not block an HTTP request. Ollama's `/api/pull` streams progress, so a background thread can track percentage while the UI polls. [Inference]
- The default `llama3.2:1b` was chosen for a practical dev-loop budget and is known to speak rough French — this story is what makes upgrading from it easy. [Source: decision-log.md 2026-09-02 wave-4 entry]
- Settings must survive `docker compose up`, so they need a bind-mounted directory; the backend container's own filesystem is recreated on every rebuild. [Inference]

## Testing

- **Approach:** integration tests against the FastAPI `TestClient` with an isolated settings directory, plus a real download and model switch against the live stack.
- **Key scenarios:** the endpoint reports all three engines; each setting round-trips and is actually consumed by the pipeline; invalid values are rejected; settings survive a reload from disk; a corrupt settings file falls back to defaults; the pull endpoint returns immediately and reports progress; a second concurrent pull is refused.
- **Per-AC verification:** AC#1 → GET the endpoint and assert all three engines; AC#2 → PUT then assert `_voice_for_language`/`get_stt_model` reflect it; AC#3 → assert the installed list and the not-installed flag; AC#4 → assert the catalogue contains Gemma entries and that a pull starts in the background; AC#5 → reset the in-memory cache and re-read; AC#6 → PUT each invalid shape and assert 400 plus no change.
- **Fixtures / mocks:** a temp `APP_DATA_DIR` per test; a stubbed pull worker so tests never download gigabytes.
- **Edge cases to cover:** Ollama unreachable (installed list unknown); a corrupt settings file; a read-only data directory.

- **Implementation notes:**
  - **Caches had to become keyed, not single-slot.** `stt._get_model()` and `tts._get_voice()` were `lru_cache(maxsize=1)`, which would have kept serving the *old* model after a change. They now take the model/voice name as an argument and cache per value, so switching loads the new one and switching back is still instant.
  - **`OLLAMA_MODEL` semantics changed:** it now seeds the settings store on first read instead of being consulted per call. `test_llm.py`'s env-var test was updated to reflect that contract rather than being worked around.
  - **Validation is strict on purpose** (AC#6): only known STT sizes, and only voices belonging to the language being set. A wrong voice would otherwise leave the pipeline unable to speak that language at all.
  - **Persistence needed a volume.** Added `./data:/app/data`; also added `piper-voices` and `whisper-cache` named volumes, which closes the follow-up logged back in wave 6 — without them, every container recreate re-downloaded whichever models you'd just picked, which would have made this feature actively annoying.
  - A corrupt or unwritable settings file is non-fatal by design: it degrades to "no overrides" rather than breaking startup.
- **Verification:** 16 new tests (71 total, all passing). Live against the running stack: changed the STT size and a French voice, confirmed both persisted to `data/settings.json` and **survived `docker compose restart`**; ran a real French turn and confirmed it downloaded and used `fr_FR-tom-medium` (the chosen voice, not the default) and cached `faster-whisper-small`; **pulled `gemma3:1b` end to end through the API** with real progress (0→27→67→100%→done), confirmed it appeared in the installed list, switched to it, and got a reply generated by it.
- **NOT verified — needs a browser:** the panel's layout, the gear toggle, and the download button's progress rendering.
